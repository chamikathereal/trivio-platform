# ADR-0001: Developer-First Payment Settlement Intelligence Platform Monorepo Architecture

## Status

**Accepted** — 2026-11-15 (Stage 1 Foundation)

## Context

Financial transactions processed via digital payment gateways, acquirers, and card schemes (Visa, Mastercard, regional networks) are subject to complex settlement cycles, tiered merchant discount rates (MDR), scheme assessments, interchange charges, cross-border levies, and bank calendar adjustments.

Historically, software developers and merchants face two unfavorable extremes:
1. Hardcoded, approximate calculations scattered across application codebases that fail to match actual bank deposits and cause reconciliation nightmares.
2. Proprietary, hosted black-box billing platforms that mandate routing customer transactional data through third-party servers, compromising developer privacy and creating vendor lock-in.

Trivio is designed from the ground up as a **developer-first payment settlement intelligence platform** (`trivio.ink`).

## Decision

We establish an npm Workspaces monorepo architecture with strict separation between pure financial calculation primitives, developer client SDKs, frontend interfaces, and hosted cloud microservices.

### 1. Monorepo Structure and Boundaries

```
trivio-platform/
├── packages/
│   ├── core/         # Pure, zero-dependency financial calculation engine
│   ├── node/         # Node.js server-side SDK foundation
│   └── react/        # Reusable UI settlement and configuration components
├── apps/
│   ├── web/          # Public marketing & calculator portal (Next.js)
│   ├── console/      # Merchant developer dashboard (Next.js)
│   ├── docs/         # Developer documentation hub (Next.js)
│   └── api/          # Hosted cloud microservice (NestJS + PostgreSQL/Prisma)
└── docs/             # Architecture, branding, roadmap, and guidelines
```

### 2. Core Principles

#### A. Developer-Owned Payment Data (Zero-Forced Ingestion)
The primary business and architectural tenet of Trivio is that developers own and store their transactional records (invoices, transaction logs, payment records, and ledger entries) inside their own databases by default.
- Using Trivio's calculation engine **does not require transmitting transaction records to Trivio Cloud**.
- Local SDK execution remains 100% functional offline without an account, API key, or active internet connection.

#### B. Separation of Concerns & Zero-Dependency Core (`@trivio.ink/core`)
- `@trivio.ink/core` contains pure mathematical and financial primitives.
- It has **zero runtime dependencies**, makes no network requests, does not read environment variables, and has no database connections.
- It operates strictly on integer minor units (e.g. cents) using `BigInt` precision to prevent floating-point inaccuracies.
- It must never contain hardcoded merchant rates, policy assumptions, or regional banking secrets.

#### C. Optional Hosted Cloud Services (`apps/api`)
Trivio Cloud provides value-add intelligence services that enhance, but do not gate, local calculations:
- Verified bank and acquirer fee schedules and rate cards
- Configurable multi-tiered merchant agreement profiles
- Bank holiday and settlement calendar intelligence
- Automated discrepancy detection and bank statement reconciliation
- Multi-tenant API key management and developer usage telemetry
- Platform persistence via PostgreSQL and Prisma is strictly restricted to `apps/api` and is only introduced when hosted services are implemented.

#### D. Clear Distinction Between Estimates and Confirmed Settlements
The platform strictly differentiates:
1. **Estimated Settlement Calculations:** Mathematical projections computed locally prior to or during transaction authorization based on active rate rules.
2. **Bank-Confirmed Settlement Events:** Cryptographically verified or statement-reconciled final credit entries confirmed by acquirer settlement batches.

## Consequences

### Positive
- Complete architectural clarity: packages can be consumed standalone in any Node.js or browser environment.
- Maximum developer trust: no involuntary telemetry or payment data capture.
- Reproducible, deterministic calculations with strict type safety.
- Clean development path: SDKs can evolve independently of backend cloud infrastructure.

### Trade-offs
- Monorepo tooling must maintain workspace boundaries without leaking dependencies between client and server packages.
- Dual maintenance of local offline calculation rules alongside cloud-synced rate cards requires robust versioning standards in future stages.
