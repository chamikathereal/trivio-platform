# ADR-0002: NestJS & PostgreSQL Multi-Tenant Data Foundation (Stage 4C.1)

## Status
Accepted

## Context
Stage 4B delivered the Trivio Developer Console (`apps/console`), an in-memory simulation tool for payment settlement modeling. To evolve Trivio into an enterprise platform, persistent data storage is required for workspaces, merchant profiles, dynamic fee schedules, clearance policies, and calculation records. 

Multi-tenancy and data isolation are critical financial requirements. We evaluated two architectural models:
1. **Separate database per tenant:** Operationally burdensome for small-to-medium payment developers.
2. **Shared relational database with workspace-scoped tenancy:** Proven, cost-effective, and enforceable via foreign keys, composite indexes, and service-layer workspace guards.

## Decisions

1. **Framework & Language:** NestJS 10 with strict TypeScript. Clean modular boundaries for workspaces, merchants, fee agreements, clearance policies, calendars, audit logs, and estimates.
2. **Persistence Layer:** PostgreSQL 16 managed via Prisma ORM 6.
3. **Workspace Isolation:** Every workspace-owned record carries a mandatory `workspaceId` foreign key with cascade deletion. All repository queries and mutation methods are strictly scoped to the authenticated caller's workspace.
4. **Deny-by-Default Security Boundary:** Business endpoints are protected by `AuthBoundaryGuard`. In production, access is blocked pending verified Stage 4C.2 authentication. In test environments, controlled identity headers permit isolated automated integration testing.
5. **Deterministic Calculation Reuse:** The `EstimatesService` does not re-implement financial math; it delegates calculation directly to `@trivio.ink/core`'s `calculatePaymentSettlementEstimate`, preserving zero-float BigInt minor units.
6. **No Cardholder Data:** The database schema strictly prohibits storing primary account numbers (PAN), CVVs, card PINs, or banking access credentials.

## Consequences
- **Positive:** Immediate testability and type-safety across backend services; strict multi-tenant boundary prevention; zero duplication of mathematical settlement engines.
- **Negative:** Full browser-based cloud login is deferred to Stage 4C.2; frontend console remains in simulation mode until identity provider integration.
